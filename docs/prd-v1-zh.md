# LetMeFit V1 产品需求文档

- 文档状态：V1 范围讨论稿
- 版本：0.1
- 更新时间：2026-04-27
- 产品类型：健康健身管理 Agent
- 产品边界：仅提供健身管理与生活方式建议，不提供医疗诊断或治疗建议

## 1. 产品概述

LetMeFit 是一个移动端健康健身 Agent，帮助用户通过拍照和语音快速记录饮食与身体指标，沉淀个人健身档案，并基于每日数据提供轻量、可执行的体重管理建议。

V1 的核心目标不是做“全能健康助手”，而是优先解决两个问题：

- 记录太麻烦，用户难以坚持
- 记录之后没有形成清晰、可执行的反馈

## 2. 产品目标

V1 需要帮助用户完成一条稳定的日常闭环：

`采集 -> 提取 -> 确认 -> 归档 -> 总结 -> 建议`

产品应当让用户能够：

- 通过餐食拍照或语音快速记录饮食
- 通过体重秤、体脂秤拍照快速记录身体指标
- 对 AI 识别结果进行快速修正
- 持续沉淀个人健身档案
- 获取简单、明确、可执行的每日建议

## 3. 目标用户

### 3.1 核心用户

- 20-40 岁一般健康成年人
- 目标偏向减脂、体重管理或建立健康习惯
- 愿意使用拍照和语音来降低记录成本
- 不希望复杂手动录入，但希望得到持续反馈

### 3.2 V1 暂不覆盖人群

- 未成年人
- 孕期用户
- 需要疾病饮食管理的人群
- 需要医疗级健康评估的人群
- 需要高阶专业训练计划的人群

## 4. 产品定位

LetMeFit 是一个“健身管理助手”，不是医疗应用，也不是泛聊天机器人。

核心价值主张：

- 降低记录摩擦
- 提高记录连续性
- 将原始记录转化为轻量行动建议
- 通过用户纠错逐步增强个体化识别效果

## 5. 核心场景

### 场景 A：餐食拍照记录

用户拍摄一张餐食照片，系统识别可能的食物、份量、热量和营养素估算结果，用户确认或修改后保存为正式记录。

### 场景 B：语音记录饮食

用户通过语音输入，例如“我中午吃了鸡胸肉沙拉和一杯无糖拿铁”，系统将语音转换为结构化饮食记录，用户确认或修改后保存。

### 场景 C：体重秤/体脂秤拍照记录

用户拍摄体重秤或体脂秤数值面板，系统提取体重、体脂率等指标，用户可以通过文字或语音修正后归档。

### 场景 D：每日总结与建议

系统在当天结束时，基于已记录数据生成简洁总结，并给出下一餐或次日的轻量建议。

## 6. V1 范围

### 6.1 包含范围

- 用户基础档案创建与编辑
- 体重管理目标设置
- 餐食拍照识别
- 语音饮食记录
- 体重秤照片识别
- 体脂秤照片识别
- 识别结果确认与修改
- 每日饮食与身体数据归档
- 每日总结生成
- 轻量饮食与习惯建议
- 用户纠错记忆能力

### 6.2 明确不做

- 医疗诊断、治疗建议、疾病管理
- 孕期、未成年人、特殊临床人群支持
- 复杂周期化训练计划
- 蓝牙硬件直连
- 社区、排行榜、商城、教练端后台
- 重型知识库平台、RAG 平台、向量检索平台

## 7. 产品体验原则

- 首页优先回答“我今天的状态如何”
- 记录入口必须足够快、足够显眼
- AI 识别结果必须容易修改
- 建议必须简短、具体、可执行
- 产品应鼓励完成记录，而不是用复杂数据压垮用户

## 8. 功能需求

### FR-1 用户档案

系统应允许用户创建和维护基础档案，包括：

- 年龄
- 性别
- 身高
- 当前体重
- 目标体重
- 活动水平
- 主要目标，如减脂或维持

### FR-2 饮食记录

系统应允许用户通过以下方式记录饮食：

- 拍摄餐食照片
- 语音描述餐食内容
- 对识别后的结构化结果进行编辑

### FR-3 身体指标记录

系统应允许用户：

- 拍摄体重秤照片
- 拍摄体脂秤照片
- 查看并修改提取结果后保存

### FR-4 识别确认与修正

系统应：

- 清晰展示 AI 提取出的字段
- 支持字段级别修改
- 支持文字或语音修正
- 将修正后的值作为正式记录保存

### FR-5 每日归档

系统应以“按天”的方式归档：

- 饮食记录
- 体重/体脂记录
- 汇总信息

### FR-6 每日总结

系统应生成每日总结，包括：

- 当日热量估算总量
- 蛋白质与主要营养素概览
- 记录完整度提示
- 近期体重趋势摘要
- 1 到 3 条可执行建议

### FR-7 Agent 个体记忆

系统应保留用户级纠错模式，包括：

- 常见食物别名
- 常见份量偏好
- 重复出现的表达方式
- 对特定食物或特定秤的常见修正

## 9. 推荐系统需求

V1 的推荐系统本质上是“建议引擎”，不是复杂的机器学习推荐平台。

### 9.1 输入

- 用户基础档案
- 用户目标
- 当日饮食记录
- 近期体重/体脂趋势
- 用户修正历史与个体记忆

### 9.2 输出类型

- 下一餐建议
- 热量控制提醒
- 蛋白质补充提醒
- 饮水、活动等习惯提醒
- 对过度激进减脂行为的谨慎提示

### 9.3 安全边界

- 输出必须是建议，不得表达为医疗结论
- 输出必须限定在一般健康生活方式范围内
- 不得主动给出极端热量限制建议
- 当数据置信度低时，应优先提醒用户确认
- 所有建议都应允许用户忽略或重新记录后再生成

### 9.4 V1 生成方式

V1 的建议生成应基于：

- 结构化营养计算
- 显式规则与安全边界
- 用户个体记忆召回
- LLM 的自然语言组织与解释

大模型不应成为唯一决策来源。

## 10. AI 提取需求

### 10.1 图像理解

系统应能够：

- 从餐食照片中识别食物候选项
- 从体重秤/体脂秤照片中提取数字指标

### 10.2 语音理解

系统应能够将语音输入转写为文本，并进一步解析为结构化记录候选项。

### 10.3 置信度处理

系统应在内部保留识别置信信息，并在低置信场景下更明确地要求用户确认。

## 11. 垂直知识体系需求

V1 需要建设轻量垂直知识体系，但不需要先建设独立知识库平台。

### 11.1 必要资产

- 食物与营养参考数据
- 常见份量假设
- 减脂、维持等目标模板
- 推荐规则
- 安全边界规则

### 11.2 V1 暂不需要

- 大规模非结构化知识检索
- 独立 RAG 系统
- 独立向量数据库

## 12. 用户记忆需求

用户记忆与通用知识不是一回事。

它主要用于记录：

- 用户常用食物叫法
- 用户常见纠错模式
- 重复出现餐食的默认映射
- 对特定表达的个体化理解偏好

用户记忆应提升后续识别与建议效果，但任何结果都必须可被用户覆盖。

## 14. 隐私与安全要求

- 产品必须清晰说明其仅提供一般健身与生活方式建议
- 涉及健康相关敏感数据时，必须有明确授权与隐私披露
- 用户必须能够在 AI 识别后进行复核和修正
- 产品不得暗示医疗级准确性
- 对高风险或超出支持范围的问题，系统应提示能力边界，而不是继续给出更强建议

## 15. 成功指标

### 15.1 激活

- 新用户完成引导的比例
- 新用户在首日完成至少 2 次记录的比例

### 15.2 效率

- 单次餐食记录的中位耗时
- 单次身体指标记录的中位耗时

### 15.3 质量

- AI 识别结果无需修改的比例
- AI 提取后最终成功保存的比例

### 15.4 留存

- 第 7 天记录留存
- 每周活跃记录天数

### 15.5 建议有效性

- 用户对每日建议的主观有用度反馈
- 每日总结页打开率

## 16. V1 发布假设

除非后续另行调整，本 PRD 先基于以下假设：

- 产品形态以移动端为主
- 推荐 iOS 优先启动
- 长期档案保存在云端
- App 本地保留缓存与草稿数据

## 17. 里程碑建议

### Phase 0：产品定义

- 确认 PRD
- 定义信息架构
- 完成低保真 Figma 流程

### Phase 1：原型验证

- 完成可点击原型
- 使用假数据跑通关键流程
- 验证记录和确认流程是否足够顺畅

### Phase 2：V1 开发

- 用户引导
- 记录采集
- AI 提取确认
- 每日归档
- 每日总结
- 轻量建议引擎

## 18. 当前待决问题

- V1 采用哪套营养数据源
- 训练记录是否放到 V1.1 再补
- Apple Health 集成是否放到 V1.1
- 每条建议需要多强的解释性

## 19. V1 范围冻结标准

当以下条件满足时，可以认为 V1 范围已冻结：

- 目标用户被确认
- 包含范围和排除范围被确认
- 核心日常闭环被确认
- 推荐系统边界被确认
- 核心数据对象被确认
- 可以进入 Figma 原型与技术方案阶段
